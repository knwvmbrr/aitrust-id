## Input and user outcome

The callable verifier receives (1) exact subject bytes, (2) a caller-selected trusted review policy, (3) signed lifecycle envelopes, and (4) an explicit local verifier clock. The CLI receives exactly those three files and uses the current local clock. It never creates keys, reads private keys, signs operating records, uploads, opens a browser, changes consent or writes files. One fixed JSON result goes to stdout; failure returns a fixed Unavailable JSON and nonzero exit without echoing paths, subject, keys or reviewer statements. Hashes and reviewer handles can still be identifying; documentation requires a private terminal/output destination.

The trusted policy is selected independently of the received history. It fixes one canonical public key/reviewer handle, exact subject SHA/byte count/version, exact review scope and sorted evidence references (SHA/byte count/type), and one externally selected chain head SHA/sequence plus a bounded freshness window. It must not be derived from the artifact being verified as automatic trust. No certificate chain, identity registry, revocation server or global completeness is implied.

Each canonical detached event is signed under that key and contains one review ID, strict sequence/previous-envelope SHA, exact subject and scope digest, issued/expiry times and action. The initial review requires explicit consent, a self-declared human reviewer and one decision (supports/does-not-support/inconclusive), plus conflict disclosure. Subsequent reviewer-signed withdrawal or supersession closes the original review and cannot silently reactivate it. A supersession points at a replacement review ID/hash only; the verifier does not fetch/follow it or bless its new scope. A new subject or scope requires a separate new explicitly reviewed record.

The verifier validates every supplied signature and the complete selected chain in order before reporting integrity. Missing/reordered/duplicate/forked events, unknown fields/profiles/algorithms, different key, altered subject/version/scope/evidence, invalid consent, stale selected checkpoint, future events or missing lifecycle head refuse. It distinguishes expired review, disclosed conflict, withdrawn and superseded states as valid signed evidence that is not an active review. Fresh active records mean only a signed review declaration is active within the selected checkpoint/window, not “independently verified.” Output retains the supplied reviewer handle and decision as attributed declarations, with signature, subject and scope evidence separately named. Identity, human status, independence, accuracy, independent timestamp and global revocation completeness remain unestablished/false; no detector pass can produce a review.

## Bounds and ownership

Subject maximum8MiB; policy maximum64KiB; complete history maximum256KiB; at most128 envelopes, one selected reviewer and one selected key of at most4096PEM bytes. Evidence references at most32; scope text at most2048characters; IDs/versions at most128characters. Existing detached parser limits/depth16/canonical serialization remain unchanged. Strict key sets and safe integer timestamps/counts reject bool/number aliases and duplicate JSON keys. Supported keys remain existing Ed25519/P-256. Checkpoint age at most7days and review lifetime at most30days are profile limits, not independently established freshness/retention promises.

One5-second monotonic validation deadline covers parsing, policy/key checks, hashes, all signatures and summary; check before/after every bounded crypto event. This is cooperative bounded synchronous work, not a claim of OS preemption; one fixed-size signature operation can complete before a timeout is surfaced. CLI capture uses nofollow/nonblocking regular files, exact pre-read caps and stable descriptor/path/ancestor checks through verification; at most3 input files/32ancestor components per path/128ownedFDs, all closes independently attempted once. Source input snapshots are held in memory; no recursive filesystem traversal, extraction, publication, replacement, deletion or output-uncertainty contract is needed because the operation is read-only. Any cleanup/read/identity failure yields Unavailable.

## Verification and risks

Before code, a different reviewer checks this contract and exact ownership. Focused actual Node controls exercise the real existing signature primitive, exact subject/scope/consent, expiry/withdrawal/supersession, chain truncation/fork/impersonation, disclosed conflicts, no-tag/nonclaim fields, duplicate JSON, bounds, timeout, nonblocking FIFO/read drift/close faults, and fixed CLI failures. A real CLI positive must verify an explicitly labeled synthetic signed fixture; no real human or private production key is represented. Test signing, if needed, imports a fixed openly documented synthetic test key only (no RNG/key-generation/new operating identity or production/release signing); no user keys or credentials are read. Record all synthetic authorship and exact source bindings. Old signature fixtures remain unchanged.

The primary risks are a caller choosing an untrustworthy key or stale head; a human falsely self-declaring independence; an omitted newer withdrawal outside the selected checkpoint; linkability of review metadata; and readers confusing integrity with truth. The schema, summary and guide explicitly preserve those limits. The verifier supplies a production function for receipt validation and lifecycle, while actual human acceptance remains separate. No template/style/timing/biometric inference, external network or model is added.
