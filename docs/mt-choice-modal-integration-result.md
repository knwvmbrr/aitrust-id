## Integration commands and boundary

From the repository root, with the existing approved verification interpreter:

```sh
python3 -m pytest tests/test_mt_choice_integration.py -q
node --test tests/mt-choice-modal-client.mjs
npm run build:site
node scripts/verify-mt-choice-site.cjs
```

`AITRUST_BUILD_PYTHON` selects the existing build interpreter and
`AITRUST_VERIFY_PYTHON` selects the trusted native comparison interpreter. These
are operator configuration, never selected by an input record. No install is
performed by these commands. A fresh checkout needs the existing pinned project
dependencies through its ordinary documented setup.

The full runner starts only its own random loopback fixtures, applies actual
reviewed response headers, and runs Chromium then WebKit sequentially. For live
publication checks reuse:

```js
const {verifyMTChoiceSite} = require('./scripts/mt-choice-site-controls.cjs');
await verifyMTChoiceSite(browser, base);
```

The live helper does not receive an owned offline fixture and reports
`{executed:false,status:'NOT_ASSESSED'}` for offline behavior. It never stops a
URL-selected or public server. Only the local runner creates and passes the
held fixture object for outage controls.

Root owns source-bound capability/CI registrations, integration of the isolated
mount/preparation/readiness deltas, generated projections, protected checks and
publication. No original requirement percentage changes in this handoff. Full
T-MT/F-019b evidence gates, human review, physical-device support and production
publication remain separate.
