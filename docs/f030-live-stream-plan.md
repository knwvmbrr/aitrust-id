# F-030: current-vendor MAIN-world stream capture

Architecture and risk plan only. Base: `4421ab58b625c8a93203f378de45ac591465b276`.
No feature activation, vendor format, live compatibility or requirement closure is established by this plan. Root owns live browser observation and integration. The implementation lane remains frozen until root reviews this plan and supplies the observed assistant framing.

## Existing system and acceptance

The installed Chrome manifest has only an ISOLATED content script on `https://chatgpt.com/*`, plus an authenticated fixed-loopback service worker. `checks_enabled` defaults off. Options disclose completed assistant-response capture, local processing, pause and reset. The content bridge binds results to page URL, response ID, text, request revision, connection and completed DOM state. Consent or credential/key changes invalidate existing results; the service worker aborts pending local-service requests when those settings change.

The separate `stream-observer.mjs` is deliberately inactive. It clones a caller-provided Response and accepts only the closed synthetic `aitrust.assistant-text.v1` SSE format. Its 2-second, 65,536-byte, 512-chunk, 8,192-character-line, 128-event and 8,000-code-unit-text ceilings are not evidence that current vendor streams fit. The installed code does not import it. Tests explicitly enforce these boundaries.

F-030 requires actual MAIN-world fetch plus tee capture and a label at the exact supported response, including a failure case and versioned evidence. DOM-only success and locally synthesized vendor-shaped streams cannot establish live fulfillment. F-037/F-035 and outside-user/accessibility acceptance remain distinct requirements; no independent detector-accuracy claim follows from capture success.

## Components and ownership

1. **Vendor parser:** a pure bounded parser separate from the synthetic observer grammar. It accepts only observed assistant-text frame paths, exact message identity and allowed transitions; it never forwards the raw frame. Mixed identities, roles, unsupported operations, duplicate/ambiguous keys, malformed UTF-8/JSON, unknown framing, missing completion and resource/deadline failures discard partial output. Actual limits require review against the observed small case; the existing synthetic observer's ceilings are not silently raised.
2. **MAIN-world wrapper:** intercept only the reviewed response route after consent activation. Forward original fetch receiver/arguments untouched, never inspect Request bodies or headers, never issue a replacement fetch, and return the host's original promise/Response objects. Attach a bounded observer to an allowed Response clone/tee; original status, headers and original-body bytes remain unchanged. Observation errors cannot reject or delay host fulfillment. Uninstall restores the prior fetch only if our exact wrapper still owns that slot; never overwrite a later page/extension wrapper. Changing fetch function identity and clone buffering effects must be disclosed and tested rather than claimed absent.
3. **ISOLATED bridge:** owns authoritative extension consent and a per-document/per-activation generation. Treat every MAIN/page message as untrusted. Validate a small closed message schema, scalar text, count/size/rate limits, generation and same-window/origin routing; do not mistake a nonce for authentication from the vendor. Never forward tokens, key material, settings or arbitrary runtime/API requests to MAIN. Require an unambiguous rendered assistant ID and exact reviewed text mapping before evaluation and rendering. If stream text and current DOM serialization differ, refuse the stream result for that response; do not label another response or disguise DOM capture as stream success.
4. **Existing local evaluator:** preserve fixed authenticated loopback destination, response signature checks, supported tags, method identity, 15-second service deadline, no telemetry and existing privacy rules. The current DOM bridge suppresses stale display; the worker aborts on settings changes, but there is no per-request cancellation message for a changed response/navigation. If stream lifecycle needs such cancellation, add a bounded request identity and sender-tab/frame/document-bound abort path, with refusal controls against cancelling another request or route. Do not claim that discarding a late result aborts an already transmitted request or retracts disclosed data. The page bridge must not gain an API that can send arbitrary destinations or bypass consent. Stream-route failure never changes tag methods or disables the default DOM route.
5. **Route selection/lifecycle:** keep DOM as the current default. Stream capture needs an explicit, separately described opt-in; previous DOM consent is not silently reused to authorize in-progress network observation. No automatic stream-to-DOM fallback presented as a successful stream check. Pause/reset, opt-out, key/token rotation, pagehide/navigation, replacement/regeneration, detached DOM and new generation cancel observation, clear buffers, invalidate results and reject late events. One selected route owns evaluation for each response; no duplicate local checks. Reload is needed if the vendor cached fetch before activation; do not rewrite vendor application code to compensate.

## Activation and consent API decision requiring root review

MAIN shares the page execution environment and cannot be trusted with extension credentials or privileged APIs. Existing authoritative consent is in the ISOLATED world and service worker. A `postMessage`, CustomEvent or DOM attribute can transport a control value, but a page can forge it. Random tokens transferred over that same page-visible channel do not create a trusted consent channel.

Two materially different activation designs must not be conflated:

- A static, same-origin MAIN bootstrap can avoid additional host permissions, remain inert by default and obey extension-issued enable/disable messages. ISOLATED and background checks can guarantee no local evaluation/extension retention while disabled. They cannot honestly prove that a hostile page cannot forge an enable message and trigger clone observation inside its own realm. A port or nonce does not remove this limit. This option needs an explicit reviewed threat-model/consent decision before implementation; the current off-by-default capture promise must not be weakened implicitly.
- Privileged `chrome.scripting` activation/teardown can originate from the extension after an explicit browser action and current settings read. It requires the `scripting` API and either an applicable host grant or temporary `activeTab` grant. Existing static content-script matches are not silently assumed to grant that API access. This changes permissions and user interaction; no broader host grant or extra permission is authorized by this plan. Any candidate must restrict execution to the exact ChatGPT top frame, leave default DOM untouched, and receive root review before changing the manifest. Navigation/revocation/failed injection must fail closed; page-visible observations still remain untrusted.

Do not implement a forgeable control channel and describe it as privileged consent. If neither reviewed design satisfies the existing authorization and capture promises, hold activation and present that precise design constraint to root.

Primary Chrome references: [content scripts and isolated worlds](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts), [scripting permissions](https://developer.chrome.com/docs/extensions/reference/api/scripting), and [activeTab user-gesture scope](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab).

## Minimized observed vendor framing and privacy finding

Root observed one intentionally synthetic, two-line reply in a fresh temporary ChatGPT conversation in live Chrome. The response used an event stream on the same-origin `/backend-api/f/conversation` route. This is a single structural observation, not a stable vendor contract. No raw event dump, request, live identifier, account data or credential is retained in this document.

The stream contained user/input/context records and a credential-bearing resume record alongside assistant output. Existing completed-response consent does not authorize reading this mixed stream. Never copy a raw stream into a fixture, receipt, bridge event, exception or log. No hook was activated; DevTools was closed after the observation.

Safely minimized shape: initial `delta_encoding` declares `v1`; a named `delta` may add a message envelope with an ID, author role, content type/parts, status, end-turn, metadata, recipient and channel. Later deltas can omit path or operation and inherit prior values. A patch operation can contain an array of path/operation/value changes, including appending text to `/message/content/parts/0` and removing a visibility metadata field. A later event can omit the operation while carrying another patch array. The final assistant message was initially hidden; subsequent patches changed visibility.

A generic JSON-patch accumulator is therefore unsafe as an assistant-only capture boundary: it would process unrelated records and inherit state that can select the wrong subject or expose hidden content. A future implementation would need a reviewed, narrow assistant-final state machine with explicit allowed inherited transitions, identity/role/channel/status/end-turn and visibility handling, strict byte/event/depth bounds, constant refusals and no raw forwarding. Unknown transitions, mixed identities, hidden/incomplete messages and unsupported patches must remain unavailable. No parser can be specified as complete from this one observation.

Assistant stream parts may contain Markdown, while the current DOM adapter serializes rendered plaintext and code. A shared ID does not prove equal subject bytes, and a finding's source spans cannot silently move between these representations. A future route must demonstrate an exact reviewed source-to-rendered-subject mapping, or refuse the stream result when that mapping is not established. Comparing only hashes of unlike representations cannot repair attribution.

Separate explicit opt-in and a reviewed activation/consent boundary are required before any real mixed-stream hook. Page-visible messages do not create trusted consent. No new permission, activation, default-route change or generic vendor-patch support is authorized here. F-030 remains 40% and open; live stream inspection is not live capture-and-label acceptance.
